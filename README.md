# OmniDesk

Омниканальный чат-инбокс для Zoho CRM. WhatsApp, Instagram, Messenger, Telegram —
в одном месте, внутри карточки CRM.

Это рабочий каркас: он собирается, проходит тесты и запускается одной командой.
Не заглушка.

```
omnidesk/
├── packages/core/          логика без побочных эффектов — покрыта тестами
│   ├── signatures.ts       проверка подписей вебхуков (Meta, Telegram, Zoho)
│   ├── crypto.ts           шифрование токенов клиентов ключом на тенанта
│   ├── normalize.ts        приведение 4 форматов к единой модели сообщения
│   ├── types.ts            UnifiedMessage + окна ответа по каналам
│   ├── db.ts               withTenant() — доступ к БД только с контекстом RLS
│   └── queues.ts           контракт очередей между сервисами
├── apps/
│   ├── ingress/            приём вебхуков: подпись → очередь → 200
│   ├── api/                REST, авторизация, подключение каналов
│   └── workers/            обработка очередей, запись в БД
├── docker-compose.free.yml  оверлей под 2 ядра / 12 ГБ бесплатного сервера
└── infra/
    ├── postgres/init/      миграции: роль app_user, RLS, схема
    ├── postgres/test-isolation.sql   ← главный тест безопасности
    ├── caddy/              TLS + CSP + frame-ancestors для Zoho
    └── scripts/            bootstrap-free.sh, harden.sh, security-check.sh, backup.sh
```

## Запуск за десять минут

**1. ВМ.** Ubuntu 24.04, 4 GB RAM, 2 ядра, 40 GB. Multipass, UTM, VirtualBox,
Hyper-V, Proxmox — что удобнее.

```bash
multipass launch 24.04 --name omnidesk --cpus 2 --memory 4G --disk 40G
```

**2. Защитить.** Вставьте свой SSH-ключ в `SSH_PUBKEY` внутри скрипта:

```bash
sudo bash infra/scripts/harden.sh
```

Создаёт пользователя `deploy`, отключает вход по паролю, настраивает UFW
и fail2ban, ставит Docker, включает автообновления безопасности и swap.

⚠️ Не закрывайте текущую SSH-сессию, пока не проверите вход в новом окне.

**3. Секреты.**

```bash
cp .env.example .env && chmod 600 .env
openssl rand -base64 32        # для каждого секрета отдельно
nano .env
```

**4. Запустить.**

```bash
docker compose up -d
docker compose logs -f api      # должно быть «Проверка целостности RLS пройдена»
```

**5. Публичный HTTPS.** Вебхуки Meta и Telegram требуют публичный адрес
с валидным сертификатом — Instagram самоподписанные отклоняет. Cloudflare
Tunnel даёт это бесплатно и **без единого открытого порта**:

```bash
# Zero Trust → Networks → Tunnels → Create → токен в CLOUDFLARE_TUNNEL_TOKEN
docker compose --profile tunnel up -d cloudflared
```

Если у сервера есть белый IP, можно вместо туннеля поднять Caddy
(`--profile public`) — сертификаты Let's Encrypt выпустятся сами.

**6. Проверить, что нигде не открыто.**

```bash
bash infra/scripts/security-check.sh
```

**7. Подключить тестового бота.**

```bash
curl -X POST https://ваш-домен/channels/telegram \
  -H "Authorization: Bearer <jwt>" \
  -H "content-type: application/json" \
  -d '{"botToken":"<токен от @BotFather>","displayName":"Тест"}'
```

Напишите боту — сообщение должно появиться в БД:

```bash
docker compose exec postgres psql -U omnidesk -d omnidesk \
  -c "SELECT content->>'text' FROM messages ORDER BY sent_at DESC LIMIT 5;"
```

## Тесты

```bash
npm test                       # 72 теста: подписи, шифрование, нормализация, окна
npx tsc --build                # типы
```

**Тест изоляции тенантов — главный тест безопасности проекта.**
Запускайте в CI при каждом изменении схемы:

```bash
docker compose exec -T postgres psql -U app_user -d omnidesk \
  -v ON_ERROR_STOP=1 -f /opt/test-isolation.sql
```

Восемь проверок: тенант видит только свои данные; явный запрос чужого
`tenant_id` даёт ноль строк; запись в чужого тенанта отклоняется; `UPDATE`
и `DELETE` не достают до чужих строк; без контекста не видно ничего;
маршрутизация работает; повторный вебхук не создаёт дубль.

⚠️ Запускать под `app_user`, а не под `postgres`. Суперпользователь обходит
RLS всегда, и тест будет зелёным при полностью сломанной изоляции.

## Три ошибки, которые нашли эти тесты

Не теоретические — все три были в первой версии кода и упали бы в проде.

**1. Воркер не нашёл бы ни одного канала.** Когда приходит вебхук, тенант ещё
неизвестен — его как раз надо определить. Но `channels` под RLS: без
выставленного `app.tenant_id` запрос возвращает ноль строк. Ни одно сообщение
никогда бы не обработалось.

Напрашивающееся решение — роль с `BYPASSRLS` для «системных» запросов. Мы
этого не делаем: такая роль умеет прочитать переписку всех клиентов сразу,
и рано или поздно через неё выполнят обычный запрос. Вместо этого минимум
данных для маршрутизации вынесен в таблицы `channel_routes` и
`zoho_org_routes` — без RLS, но и без пользовательских данных. **В системе
не существует соединения, способного прочитать чужую переписку.**

**2. Сброс контекста ронял транзакцию.** `current_setting('app.tenant_id', true)`
возвращает `NULL`, если параметр не выставляли, но **пустую строку**, если
его сбросили. Приведение `''::uuid` падает с ошибкой. Лечится `NULLIF(..., '')`
в политике: при сбросе контекста запрос обязан вернуть ноль строк, а не
уронить транзакцию, иначе ошибка в управлении контекстом превращается в отказ
обслуживания.

**3. Дедупликация не работала.** `messages_dedupe_idx` — частичный уникальный
индекс (`WHERE external_id IS NOT NULL`, потому что у исходящих сообщений
его ещё нет до отправки). `ON CONFLICT` не находит частичный индекс без
повторения предиката и падает с «no unique or exclusion constraint matching».
Meta ретраит вебхуки до 7 дней — это была бы лавина дублей в инбоксе.

## Что важно знать перед доработкой

**Доступ к БД — только через `withTenant()`.** Никакой код не обращается к пулу
напрямую. Это единственный способ гарантировать, что контекст RLS выставлен.
Заведите ESLint-правило, запрещающее импорт `pool` за пределами `db.ts`.

**Третий аргумент `set_config` обязан быть `true`.** Иначе значение утечёт на
следующий запрос, который возьмёт это же соединение из пула. Самая опасная
ошибка в мультитенанте: проявляется редко, под нагрузкой, и выглядит как
«клиент увидел чужие данные».

**Каждая новая таблица с `tenant_id` — сразу `SELECT apply_tenant_rls('...')`**
в той же миграции. Приложение проверяет это на старте и не запустится при
нарушении.

**HMAC считается от сырого тела запроса.** `JSON.parse` с последующей
пересериализацией меняет байты — подпись не сойдётся, и вы полдня будете
искать несуществующую ошибку в секрете. В `ingress` для этого стоит
собственный content-type parser.

**Токены не попадают в логи.** Ни целиком, ни в Sentry. Для отладки есть
`maskSecret()` — показывает последние четыре символа.

**`ENCRYPTION_MASTER_KEY` нельзя потерять.** Им зашифрованы токены каналов
и Zoho-токены всех клиентов. Потеряете — придётся переподключать каждый
канал каждого клиента вручную. Копия в менеджере паролей, отдельно от сервера.

## Что здесь ещё не реализовано

Каркас покрывает приём сообщений от начала до конца. Дальше по роадмапу
из основного документа:

- отправка сообщений (очередь `outbound`, лимиты по каналам, шаблоны WhatsApp);
- скачивание медиа в объектное хранилище (очередь `media`);
- OAuth Zoho с поддержкой всех дата-центров + резолв контактов через COQL;
- Embedded Signup для WhatsApp;
- ZET-расширение с тремя виджетами;
- фронтенд инбокса;
- Instagram и Messenger (нормализаторы пишутся по образцу WhatsApp).

Порядок и сроки — в документе «Техническая архитектура и план запуска».
